## 一、重要技术决策

### 1. 单文件 FastAPI + SQLite + 服务端渲染 HTML
**为什么**：第一阶段的核心价值是把"导入→认领→权限边界→审计"这套**业务流程和权限模型**跑通并能随时给财务演示、快速改流程，**不是前端精美度**。前后端分离、引 Vue/React、上 ORM 都会拖慢这个目标。单文件 + 原生表单 + 内联 HTML 让"改流程"成本最低、部署最简单（一个进程 + 一个 db 文件）。
**代价/边界**：文件会变大（现约 4800 行）、HTML 内联可维护性差。这是**明知的权衡**，规模可控时不要急于重构。

### 2. 飞书 OAuth/发消息全部用标准库 urllib 手写，不引飞书 SDK
**为什么**：保持零额外依赖、流程完全可控、部署无坑。飞书的几个端点（authorize / oauth token / user_info / im messages / tenant_token）都是简单的 HTTP 调用，`_feishu_request` 一个封装就够，不值得为此引入 SDK 或 requests/httpx。
**注意**：urllib 自动读环境变量代理（开发机走 clash），云端直连飞书即可。

### 3. 会话用 HMAC 签名 cookie，不用服务端 session 存储
**为什么**：无需额外存储/中间件，进程重启不丢登录（只要 `SESSION_SECRET` 不变），实现简单。cookie 里只放 `{id, name, src, exp}`，用 HMAC-SHA256 签名防篡改（`make_session`/`read_session`）。

### 4. 角色不写进会话，每请求实时 `compute_role()`（关键决策，有演进）
**最初**：登录时把角色算好写进 session cookie。**问题**：超管在后台把某人设为管理员后，对方得**退出重登**才生效（角色被冻结在旧 cookie 里），体验差，也和"免改配置即时生效"的目标矛盾。
**改为**：会话只存身份（open_id/name），角色每次请求实时算：超管白名单 → 数据库 `app_users.managed_role` / 旧字段 `is_admin` → 否则 claimant。**这样超管或管理员调整身份后，对方刷新页面立即生效。** 代价是每请求一次小查询（SQLite 本地极快，内部工具完全可接受）。

### 5. 三级权限：超管走 `.env` 白名单（根），管理员存数据库
**为什么**：必须有个"根权限"不能全靠数据库——否则**鸡生蛋**（没人能授权第一个管理员）。所以超管由 `.env` 的 `FEISHU_SUPERADMIN_OPEN_IDS` 钉死（改它要动配置），普通管理员和事业部总经理等托管身份存 `app_users.managed_role`、免改配置即时生效。旧字段 `is_admin` 仅为兼容早期管理员逻辑。**不要把超管也挪进数据库。**

### 6. `catalog.json` 作为分类数据源，与代码分离
**为什么**：部门/中心/项目会频繁调整（项目期间改了多次：年会改名、拆中台、加中心/项目）。把三级分类放进独立 JSON，改分类只动数据文件、不碰代码、不用改逻辑。前后端都从它取值并双重校验。

### 7. 认领分类从"自由文本"演进到"三级联动单选"
**演进**：最初部门是自由输入 → 改固定下拉（防错字）→ 拿到公司产品分类 Excel 后改「部门→中心→项目」三级联动单选 + 后端强校验三级匹配。
**为什么**：自由文本会产生脏数据、对不上账；联动单选保证认领归属落到标准分类，便于后续统计。

### 8. 数据库迁移用 `ensure_column` 幂等加列
**为什么**：上线后的库不会因为改了 `CREATE TABLE` 就自动变更。新增字段（如 `claimed_team`、`app_users` 表）用 `ensure_column`/`CREATE TABLE IF NOT EXISTS` 在 `init_db` 里幂等执行，**不丢已有数据**。后续加字段沿用此模式。

### 9. 待认领列表恢复显示金额，并补充“到款公司”
**为什么**：试用后业务反馈，普通用户在提交认领时必须同时看到金额、付款方、备注和实际收款主体，否则容易误认领。原先“隐藏金额保护财务信息”的设计被实际使用场景推翻。当前口径：认领搜索和待认领列表都展示金额；同时新增 `receiver_company` 记录集团下实际收到款的公司。后续不要再按旧决策把金额列隐藏。

### 10. 项目目录采用“JSON 基础目录 + SQLite 覆盖层”
**为什么**：部门和中心仍是稳定的组织结构，适合由 `catalog.json` 统一维护；项目变化更频繁，需要财务在后台自助增删。如果直接改应用目录里的 JSON，云端重新部署可能覆盖运行期修改；所以将财务操作写入持久化 SQLite，启动时合并为运行时 `CATALOG`。
**删除语义**：删除是记录 `active=0` 的停用覆盖，项目从后续认领选项中消失，但已写入 `claims`/`payments` 的历史文本不改。再次添加同名项目即恢复为 `active=1`。不开放新增部门或中心，也不允许删除一个中心的最后一个可用项目。

### 11. 跨部门协作用“参与范围”解决，不改用户主身份
**为什么**：大型会议招生期间，一个同事可能平时属于培训中心，但临时参与年会报名组。如果直接改主身份，会影响日常数据口径；如果做多个账号，使用成本高。当前方案是在 `user_scopes` 中给成员增加额外参与范围，个人中心提供“全部角色 / 主身份 / 单个参与范围”切换。主身份仍保留，额外范围只影响看板查看范围。

### 12. 批量采购用“分摊认领”，不做线下二次拆分
**为什么**：客户一次性采购多个产品时，先由一个人整笔认领再线下分配，会造成后续对账和责任归属不清。当前方案是在 `/split-claim` 页面直接把一笔到款拆成多条部门/中心/项目/金额明细，每条分摊提交后直接成为已认领明细，财务在后台逐笔检查并可驳回退回。这样复杂采购从一开始就结构化留痕。

## 二、曾尝试但放弃的方案

### 1. 飞书自动读取组织架构部门 —— 放弃
**尝试**：想让用户飞书登录后自动带出其所在部门。为此开通了通讯录权限、调 `contact/v3/users` 和 `contact/v3/departments`。
**为什么放弃**（三个真实障碍）：
- **口径不一致**：飞书是**行政组织架构**（如"中国教育创新年会事业部"），`catalog.json` 是**业务认领分类**（如"年会/中国教育创新年会事业部"下的中心/项目），两套体系不是一一对应，自动读到飞书部门也落不到认领分类上，还得维护映射表。
- **权限拿不全**：完整通讯录读取权限 `contact:contact:readonly`（中文"读取通讯录"）在开发者后台**搜不到**（飞书收窄了粗粒度权限）；细粒度 `contact:contact.base:readonly` 只返回部门 **ID 不返回 name**。
- **还要配数据权限范围**：光有 API scope 不够，不配"通讯录数据权限范围"会报 `40004 no dept authority`。
**最终方案**：部门改为**用户首次登录自选 + 管理员后台调整**。那些通讯录权限虽已在飞书后台开通，但**运行代码并未使用**（后续可在飞书后台回收）。

### 2. trycloudflare 临时隧道作为长期访问方式 —— 仅限开发，不可用于生产
见下方"踩坑"。结论：临时隧道地址会变、会失效，**只能开发期临时用**，生产必须正式部署（见 `DEPLOY.md`）。

### 3. git 用 token + keychain 记住凭证 —— 改用 SSH key
**为什么**：token 在聊天里出现过、且会过期；改用 SSH key（公钥可公开、私钥留本地、不过期），且因国内 22 端口受限，配了 `ssh.github.com:443`。现已 SSH 免密推送。

## 三、已踩过的坑（飞书集成为主，最值得后人警惕）

### 飞书相关
1. **OAuth 端点版本**：用的是新版标准 OAuth2 —— 授权 `accounts.feishu.cn/open-apis/authen/v1/authorize`、换 token `open.feishu.cn/open-apis/authen/v2/oauth/token`（注意是 **v2**，传 `client_id/client_secret`）、用户信息 `authen/v1/user_info`。改动前务必对照飞书最新文档，别用废弃的旧版 index/access_token。
2. **API 权限 ≠ 数据权限范围**：加了 `contact:contact.base:readonly`（API scope）后仍报 `40004 no dept authority`，因为还要在「开发配置→权限管理→数据权限」里配**通讯录权限范围**（选全部成员）。两者是分开的。
3. **base 权限只给 ID**：`contact.base:readonly` 拿到的部门/用户 **name、department_ids 都是 None**，要更高权限才有内容。
4. **权限搜索按中文名**：飞书后台权限搜索框按**中文权限名**匹配，搜英文 scope id 搜不到（如 `contact:contact:readonly` 要搜"读取通讯录"）。
5. **发消息三要素缺一不可**：以应用身份给用户发飞书消息，需要 ① 权限 `im:message:send_as_bot`（中文"以应用的身份发消息"）② 应用**开启「机器人」能力** ③ **接收人在应用可见范围内**。少任何一个都发不出（错误码 99991672 缺权限、230013 不在范围、230027 缺权限）。
6. **加权限后必须重新发布版本**才生效——多次卡在"加了权限但没发布"。
7. **回调地址三处必须一致**：`.env` 的 `FEISHU_REDIRECT_URI`、飞书后台「重定向 URL」、代码生成的授权链接，三者要完全相同，否则登录失败。换部署地址时三处同步改 + 飞书重新发布。

### 安全
8. **越权漏洞（已修）**：早期管理路由用表单/URL 传来的 `role` 字段鉴权，可被伪造提权。已加固为：敏感路由只用**签名会话**判角色（`actor_from_request`→`compute_role`），无会话强制 `claimant`，URL `?role=admin` 和表单伪造均实测 403。**不要倒退到信任客户端传的角色。**

### 部署/隧道（开发环境）
9. **cloudflared QUIC 在 clash TUN 代理下连接反复断**（日志 `control stream failure` / `Tunnel not found`）。解法：`cloudflared tunnel --protocol http2`（走 TCP 443，被代理正常转发）。
10. **trycloudflare 临时隧道跨天失效**，且残留进程会让新隧道也起不来（报 `Unauthorized: Tunnel not found`）——需 `pkill -9 -f cloudflared` 彻底清掉再重起。
11. **本机 `python3` 指向问题**：开发机默认 `python3` 是 `~/.local/bin/python3`（没装 uvicorn），要用 `/usr/bin/python3 -m uvicorn`。**这是那台机器的环境问题，不是项目要求。**
12. **curl 测试中文/未编码 URL** 会报 400 "Invalid HTTP request"——是测试姿势问题，不是代码 bug，用 `--data-urlencode`。

## 四、已知限制

1. **SQLite 单文件**：适合当前小规模（内部工具、几十人）。并发写多、数据量大需迁 PostgreSQL。
2. **单文件 `app.py` 约 4800 行、HTML 内联**：增长后维护成本上升，但当前刻意保持简单。
3. **自动化测试仍少**：已有 `tests/test_excel_import.py` 覆盖导入、部分认领、本人取消、分摊认领等关键逻辑；复杂页面仍主要靠 curl/浏览器回归。
4. **飞书部门不自动同步**：靠用户自选 + 管理员调整（见放弃方案 1）。
5. **驳回通知依赖可见范围**：接收人不在飞书应用可见范围内会发送失败（功能容错、不报错，但人收不到）。
6. **数据库不在版本控制**：业务数据需单独备份；本地库可清空，但正式服务器的持久化 SQLite 不会随 git 同步。
7. **当前未正式部署**：仅临时隧道，地址不稳。

## 五、后续开发需要避免的问题（红线清单）

1. **绝不**把角色写回会话 cookie，**绝不**信任表单/URL 的 `role` 做鉴权——角色必须由会话 + `compute_role` 实时算。
2. **绝不**把飞书 Secret、`SESSION_SECRET` 提交进 git（`.env` 已 gitignore，新增敏感项同步更新 `.env.example`）。
3. 改飞书部署地址 → `.env` + 飞书后台「重定向 URL」+ 飞书**重新发布**，三步缺一登录就挂。
4. 飞书加任何权限/能力后，**必须重新发布版本**才生效。
5. 飞书读数据要同时满足「API 权限 + 数据权限范围」；发消息要满足「权限 + 机器人能力 + 可见范围」。
6. 数据库改字段走 `ensure_column`，别写会丢数据的 DDL；别期望改 `CREATE TABLE` 能影响已上线的库。
7. 所有进 HTML 的数据走 `esc()`，所有 SQL 参数化——别图省事拼字符串。
8. 金额单位是**分**（`amount_cents`），涉及金额改动注意 `parse_amount`/`money` 换算。
9. **不要用 trycloudflare 临时隧道做生产**——按 `DEPLOY.md` 正式部署。
10. 超级管理员只能在 `.env` 白名单，别挪进数据库（会丢失授权的"根"）。
11. `catalog.json` 只维护基础部门/中心/项目；财务在后台的项目增删存在 `catalog_project_changes`，不要只用 JSON 覆盖运行时目录。
12. 普通用户现在需要看到金额和到款公司来核对认领；不要恢复到旧的“待认领列表隐藏金额”设计。
13. 后台导入入口面向财务上传文件，不再展示 CSV/TSV 文本粘贴框；如需恢复粘贴入口，先确认财务真实使用场景。
