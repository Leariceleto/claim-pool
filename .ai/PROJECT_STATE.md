## 维护协议（写给维护本项目的 AI——包括你）

**铁律：每完成一个开发任务、提交代码前，必须更新本文件，并随代码一起提交。** 这样本文件永远反映最新状态，新 AI 只读它就能接手。

每次更新做四件事：
1. 更新顶部「**最后更新**」的日期和提交说明。
2. 在「**最近完成**」顶部加一条（倒序，**只保留最近 6 条**，更早的删掉——历史决策去 `DECISIONS.md` 查，不在这里堆积）。
3. 调整「**当前待办**」：完成的划掉/移除，新出现的加上，按优先级排。
4. 更新「**已知问题**」：修掉的删除，新发现的补上。

写的时候保持简洁、只写"现在的事实"，不写过程叙述。其他 `.ai/*.md` 文档（架构、决策、规则）是相对稳定的参考，**只在对应内容真正变化时才改**；高频变动的状态只放本文件。

## 已知问题

- 临时隧道（trycloudflare）地址会变、跨天失效，仅开发期可用（正式部署后消失）。
- 飞书部门未自动从组织架构读取，靠用户首次自选 + 管理员后台调整（原因见 `DECISIONS.md`，是有意取舍）。
- 本地 `claim_pool.db` 不随 git 同步，可能含本机验证或重新上传的数据；正式服务器如果挂了持久化 SQLite，需要在服务器上单独备份/清空。
- 驳回通知依赖接收人在飞书应用可见范围内，范围外发送失败（容错不报错，但人收不到）。
- 入池群通知依赖 `FEISHU_NOTIFY_CHAT_ID`、机器人入群、`im:message:send_as_bot` 权限和应用重新发布；未配置或发送失败不阻断确认入池。
- 单文件 `app.py`（约 4800 行、HTML 内联），已有少量回归测试，复杂页面仍主要靠手动验证。
- SQLite 单文件，适合当前小规模（内部工具、几十人）；并发写多/数据量大需迁 PostgreSQL。数据库不在 git，需单独备份。
